## Scope of the current work — proxy first, LiveScript's own SDK usage is out of scope

Luís drew a boundary msilva had been blurring:

> *"Teu primeiro trabalho é botar o proxy funcionando 100%. O teu trabalho não é
> botar o [...] live script funcionando [...] considera que o que tá sendo pelo SDK
> a gente não tá querendo olhar agora."*

Concretely: LiveScript calls Airtable through **both** the `airtable` SDK and hand-built
REST calls. Getting `X-App-Id` onto *all* of that traffic is a LiveScript-side
concern that can wait; getting the **proxy itself** validated and correct is the
actual job. **Partial migration is fine and expected**, not a failure state:

> *"a gente não quer sair de zero para 100% [...] de todas as chamadas que a gente
> faz, 30% só vai passar pela TI. É um problema? Não, não é um problema, é uma
> necessidade identificada."*

This reframes the SDK-vs-REST-transport split already documented on
[[How LiveScript sends the proxy X-App-Id header]] — msilva already validates via
plain HTTP requests (*"eu consigo validar pelo pelo só pelas requisões HTTP"*)
without touching the SDK path at all, and per this conversation that's an
acceptable place to stop for now, not a gap to close urgently.

## LiveScript's Next.js caching — a false alarm, not a bug

msilva raised a concern: LiveScript's **events page** caches requests heavily in the
browser, to the point that a proxy-side change causing a 401 didn't surface for
~30 minutes because the cached responses kept serving. He read this as a testing
hazard.

**Luís's correction: this is intentional and correct for that specific page** — the
events data changes rarely, so aggressive caching is the right call, not a defect.
He redirected msilva to the actual heavy-use screen — the real-time collaborative
script editor, where every keystroke and lock hits the network with no such
caching — as the place proxy validation actually matters. Confirms and extends
[[LiveScript]]'s existing framing: the editor screen is where Airtable pressure
concentrates; the events page is not representative of it.

## Tooling feedback — Claude Code verbosity, and how Luís fixes it

msilva raised, unprompted, that he's finding Claude Code more verbose than what he
was used to with GPT-based tooling (Cursor). Concrete complaint: PR descriptions
came out *"terrível"* — overly long.

**Luís's response: this is fixable, and the fix is to pin the desired behavior into
the project once, not to tolerate it or switch tools.** He demonstrated live: he'd
just told Claude to never generate an HTML artifact directly and always ask first,
after it kept doing so unprompted — *"adiciona uma instrução no cloud [...] ele não
vai mais fazer, vai se comportar do jeito que eu quero [...] Se você não [...]
orientá-lo a fazer dessa forma, ele vai continuar fazendo."*

Framed as one instance of a general practice: **treat an unwanted response the way
you'd treat messy code you happen to pass through** — fix it in place, in the
project's persistent instructions, the first time you see it. Direct field
application of the *"agent instructions belong in files, not memory"* lesson
already on [[Agent Flow]] (from
[[Gabriel Packer - solo founder AI workflow (part 1)]]) — now demonstrated by
Luís himself, on Claude Code specifically. Full write-up, including the other
tooling recommendations from this exchange: [[Claude Code Working Habits]].

Also recorded: **Claude Code defaults toward "vibe coding"** in Luís's view —
*"ele te direciona menos para você amarrar as coisas [...] você tem que dar esse
passo proativamente."* His own experience with it has otherwise been positive
(*"pra mim tem sido perfeito"*), with one live exception on a different project (with
Yasmin) where an earlier over-specified instruction is now actively working against
him and needs unwinding — noted as a caution that instructions accumulate and need
revisiting, not just adding to.
